* Introduction
If you write code, notes, configs, or scripts, you will eventually want a history of what changed and a place to keep that history online. That is what [[https://git-scm.com/][Git]] and [[https://github.com/][GitHub]] are for.

Git runs on your machine. It tracks versions of your files. GitHub is a website (and a set of services) that hosts Git repositories so you can back them up, share them, and collaborate.

This post is a full path from zero to a live repository on GitHub using only the terminal. The same Git commands work on *macOS* and *Windows*. The install steps and which terminal you open are the main differences.

By the end you will:

1. Install Git on Mac or Windows
2. Configure your name and email
3. Sign in to GitHub from the terminal
4. Create a small sample project called =notes-cli=
5. Commit, push, branch, and pull like a normal day-to-day workflow

* What you will use
- *Git* — the version-control tool in your terminal
- *GitHub* — where the remote copy of your project lives
- *A terminal*:
  - *macOS*: Terminal.app, iTerm2, or Warp
  - *Windows*: *Git Bash* (recommended for this guide), or PowerShell after Git is installed

Git commands themselves are the same. Paths look a little different (=/Users/...= on Mac, =C:\Users\...= or =/c/Users/...= in Git Bash on Windows).

* Install Git
** macOS
**Option A — Homebrew** (clean and easy to update):

#+begin_src sh
brew install git
#+end_src

**Option B — Xcode Command Line Tools** (ships Git with Apple’s tools):

#+begin_src sh
xcode-select --install
#+end_src

Check that Git works:

#+begin_src sh
git --version
#+end_src

You should see something like =git version 2.x.x=.

** Windows
1. Download the installer from [[https://git-scm.com/download/win][git-scm.com/download/win]]
2. Run it and keep the defaults unless you know you need something else
3. Important defaults for beginners:
   - Editor: whatever you prefer (VS Code, Notepad++, or Vim)
   - Adjust PATH: *Git from the command line and also from 3rd-party software*
   - Line endings: *Checkout Windows-style, commit Unix-style* is fine for most people
4. After install, open *Git Bash* from the Start menu

Verify:

#+begin_src sh
git --version
#+end_src

*Note:* On Windows, this guide assumes *Git Bash*. If you use PowerShell, the Git commands are the same; only shell shortcuts (=ls=, =touch=) may differ.

* Open a terminal
** macOS
- Spotlight: =Cmd + Space=, type =Terminal=, press Enter
- Or open *Applications → Utilities → Terminal*

** Windows
- Start menu → search *Git Bash* → open it
- Or open *PowerShell* / *Windows Terminal* if Git is on your PATH

Pick a folder where you keep projects. Examples:

#+begin_src sh
# macOS
cd ~/Developer

# Windows (Git Bash)
cd ~/Documents
#+end_src

If the folder does not exist yet:

#+begin_src sh
mkdir -p ~/Developer
cd ~/Developer
#+end_src

On Windows PowerShell you can use:

#+begin_src powershell
mkdir $HOME\Developer
cd $HOME\Developer
#+end_src

* First-time setup
Do this once per machine.

** Set your identity
Git stamps every commit with a name and email. Use the email tied to your GitHub account (or your GitHub noreply address).

#+begin_src sh
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
#+end_src

** Sensible defaults
#+begin_src sh
git config --global init.defaultBranch main
git config --global pull.rebase false
git config --global core.editor "nano"
#+end_src

On Windows, if you prefer Notepad or VS Code:

#+begin_src sh
# Notepad
git config --global core.editor notepad

# VS Code (if `code` is on PATH)
git config --global core.editor "code --wait"
#+end_src

** Confirm
#+begin_src sh
git config --global --list
#+end_src

* Authentication with GitHub
You need a [[https://github.com/signup][GitHub account]] first. Then choose one way to authenticate when you =git push= and =git pull=.

** Option A — GitHub CLI (easiest for most people)
Install =gh=:

#+begin_src sh
# macOS (Homebrew)
brew install gh

# Windows (winget, in PowerShell)
winget install --id GitHub.cli
#+end_src

Or download from [[https://cli.github.com/][cli.github.com]].

Then log in:

#+begin_src sh
gh auth login
#+end_src

Follow the prompts:

1. GitHub.com
2. HTTPS (simple) or SSH (if you already use keys)
3. Login with a web browser
4. Authorize when the browser opens

Check:

#+begin_src sh
gh auth status
#+end_src

** Option B — HTTPS with a Personal Access Token (PAT)
If you skip =gh=, GitHub no longer accepts your account password for Git over HTTPS. You create a *token* instead:

1. GitHub → *Settings* → *Developer settings* → *Personal access tokens*
2. Generate a token with =repo= scope (classic) or the fine-grained equivalent
3. When =git push= asks for a password, paste the *token*, not your GitHub password

** Option C — SSH keys
Good long-term setup. Generate a key, add the public key to GitHub, then use =git@github.com:USER/REPO.git= remotes.

#+begin_src sh
# macOS / Git Bash
ssh-keygen -t ed25519 -C "you@example.com"
#+end_src

Press Enter to accept the default path. Then:

#+begin_src sh
# macOS: start agent and add key
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# copy public key
# macOS
pbcopy < ~/.ssh/id_ed25519.pub
# Windows Git Bash
clip < ~/.ssh/id_ed25519.pub
#+end_src

On GitHub: *Settings → SSH and GPG keys → New SSH key* → paste → save.

Test:

#+begin_src sh
ssh -T git@github.com
#+end_src

You should see a greeting that includes your username.

For the sample project below we will use *HTTPS + GitHub CLI*, because it is the shortest path for beginners on both Mac and Windows.

* Core commands you will use daily
Memorize this loop:

| Command | What it does |
|---------+--------------|
| =git status= | What changed? What is staged? |
| =git add <file>= | Stage a file for the next commit |
| =git add .= | Stage everything in this folder |
| =git commit -m "message"= | Save a snapshot locally |
| =git push= | Send commits to GitHub |
| =git pull= | Fetch + merge remote changes |
| =git log --oneline= | Short history |
| =git branch= | List branches |
| =git checkout -b name= | Create and switch to a branch |
| =git switch name= | Switch branches (newer syntax) |
| =git clone <url>= | Download an existing repo |

Other useful ones:

#+begin_src sh
git diff              # unstaged changes
git diff --staged     # staged changes
git restore file.txt  # discard local edits to a tracked file
git restore --staged file.txt  # unstage, keep edits
#+end_src

* Sample project: notes-cli
We will build a tiny project from scratch, put it on GitHub, then practice a feature branch. The project is a small shell script that appends dated notes to a file — enough structure to feel real, small enough to finish in one sitting.

** 1. Create the project folder
#+begin_src sh
cd ~/Developer   # or wherever you keep code
mkdir notes-cli
cd notes-cli
#+end_src

** 2. Turn the folder into a Git repository
#+begin_src sh
git init
#+end_src

You should see something like =Initialized empty Git repository in .../notes-cli/.git/=.

** 3. Create the files
Create =README.md=:

#+begin_src sh
cat > README.md << 'EOF'
# notes-cli

A tiny command-line notes helper.

## Usage

```bash
./note.sh "Buy milk"
./note.sh "Ship the blog draft"
```

Notes are appended to `notes.txt`.
EOF
#+end_src

Create the script =note.sh=:

#+begin_src sh
cat > note.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

NOTE="${*:-}"
if [ -z "$NOTE" ]; then
  echo "Usage: ./note.sh \"your note\""
  exit 1
fi

STAMP="$(date '+%Y-%m-%d %H:%M:%S')"
echo "[$STAMP] $NOTE" >> notes.txt
echo "Saved: $NOTE"
EOF
#+end_src

Make it executable (macOS and Git Bash):

#+begin_src sh
chmod +x note.sh
#+end_src

Add a =.gitignore= so temporary junk never gets committed:

#+begin_src sh
cat > .gitignore << 'EOF'
.DS_Store
Thumbs.db
*.tmp
EOF
#+end_src

** Windows note:** If =cat > file << 'EOF'= feels awkward in PowerShell, create the same files in your editor (VS Code, Notepad) with the same names and contents, then continue with Git commands.

** 4. Check status and make the first commit
#+begin_src sh
git status
git add README.md note.sh .gitignore
git status
git commit -m "Initial commit: notes-cli script and README"
#+end_src

First commit tip: if Git complains that you have no identity set, go back to *First-time setup*.

View history:

#+begin_src sh
git log --oneline
#+end_src

** 5. Create an empty repository on GitHub
With GitHub CLI (from inside =notes-cli=):

#+begin_src sh
gh repo create notes-cli --public --source=. --remote=origin --push
#+end_src

That one command:

- Creates =notes-cli= under your GitHub account
- Adds =origin= as the remote
- Pushes =main=

Without =gh=, do it manually:

1. On github.com click *New repository*
2. Name it =notes-cli=
3. Leave it empty (no README, no .gitignore — you already have those locally)
4. Then in your terminal:

#+begin_src sh
git remote add origin https://github.com/YOUR_USERNAME/notes-cli.git
git push -u origin main
#+end_src

Replace =YOUR_USERNAME= with your GitHub username.

Open the repo in the browser:

#+begin_src sh
gh repo view --web
# or visit https://github.com/YOUR_USERNAME/notes-cli
#+end_src

** 6. Try the app once
#+begin_src sh
./note.sh "First note from my machine"
./note.sh "Learning Git on the terminal"
cat notes.txt
#+end_src

=notes.txt= was created by the script. Decide if you want it in Git. For this sample we *will* track it so the repo shows real usage.

#+begin_src sh
git add notes.txt
git commit -m "Add sample notes file from first runs"
git push
#+end_src

** 7. Practice a feature branch
Branches let you work without touching =main= until you are ready.

#+begin_src sh
git checkout -b feature/list-command
# or: git switch -c feature/list-command
#+end_src

Update =note.sh= so =./note.sh --list= prints notes:

#+begin_src sh
cat > note.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

if [ "${1:-}" = "--list" ] || [ "${1:-}" = "-l" ]; then
  if [ ! -f notes.txt ]; then
    echo "No notes yet."
    exit 0
  fi
  cat notes.txt
  exit 0
fi

NOTE="${*:-}"
if [ -z "$NOTE" ]; then
  echo "Usage: ./note.sh \"your note\""
  echo "       ./note.sh --list"
  exit 1
fi

STAMP="$(date '+%Y-%m-%d %H:%M:%S')"
echo "[$STAMP] $NOTE" >> notes.txt
echo "Saved: $NOTE"
EOF
#+end_src

#+begin_src sh
chmod +x note.sh
./note.sh --list
#+end_src

Commit and push the branch:

#+begin_src sh
git add note.sh README.md
# optional: update README Usage section to mention --list
git commit -m "Add --list flag to print saved notes"
git push -u origin feature/list-command
#+end_src

Open a pull request on GitHub:

#+begin_src sh
gh pr create --title "Add list command" --body "Adds ./note.sh --list to print notes.txt"
#+end_src

Or click *Compare & pull request* on GitHub after the branch push.

Merge it (on GitHub, or):

#+begin_src sh
gh pr merge --merge
#+end_src

Back on your machine, update =main=:

#+begin_src sh
git checkout main
git pull origin main
#+end_src

You now have the full loop: local project → commits → GitHub → branch → PR → merge → pull.

* Using a =dev= branch so you do not break =main=
On many projects you keep =main= as the *stable* line (what works, what you deploy, what other people clone). You do *not* want half-finished features sitting on =main= and colliding with someone else’s work — or with your own “I need a clean copy” moment.

So you create a long-lived =dev= branch (sometimes called =develop=). You build and try features there. When a batch of work is ready, you merge =dev= into =main=.

Think of it like this:

| Branch | Role |
|--------+------|
| =main= | Stable. Only merge finished work here. |
| =dev= | Active development. New features land here first. |
| =feature/...= | Optional short branch for one feature, then merge into =dev= |

**Create =dev= from =main= (once)**

Make sure =main= is up to date, then branch:

#+begin_src sh
git checkout main
git pull origin main
git checkout -b dev
# or: git switch -c dev
git push -u origin dev
#+end_src

On GitHub you can also set =dev= as the default branch for PRs later, but beginners often leave =main= as the default and only merge into it when ready.

**Do your feature work on =dev=**

Example: add a =--clear= flag to =notes-cli= without touching =main=.

#+begin_src sh
git checkout dev
git pull origin dev
#+end_src

Edit =note.sh= (add a clear command), then:

#+begin_src sh
# after you edit note.sh...
./note.sh --clear   # only if you implemented it
git status
git add note.sh
git commit -m "Add --clear to wipe notes.txt"
git push origin dev
#+end_src

=main= is unchanged. Anyone cloning =main= still gets the last stable version. You are free to experiment on =dev=.

**Optional: feature branch off =dev=**

If the change is big, branch from =dev= instead of committing straight to =dev=:

#+begin_src sh
git checkout dev
git pull origin dev
git checkout -b feature/clear-notes
# implement, commit...
git push -u origin feature/clear-notes
gh pr create --base dev --title "Add --clear" --body "Wipes notes.txt when requested"
#+end_src

Notice =--base dev=: the pull request targets =dev=, not =main=. That keeps unfinished work out of the stable branch.

**When you want to merge =dev= into =main=**

Only do this when =dev= is in good shape (features work, you are ready for a “release”).

*Option A — pull request on GitHub (recommended)*:

#+begin_src sh
gh pr create --base main --head dev --title "Merge dev into main" --body "Stable batch of notes-cli updates"
gh pr merge --merge
#+end_src

Or on GitHub: *Pull requests → New* → base =main=, compare =dev= → create → merge.

*Option B — merge locally*:

#+begin_src sh
git checkout main
git pull origin main
git merge dev
git push origin main
#+end_src

Then keep =dev= moving forward from the updated =main=:

#+begin_src sh
git checkout dev
git merge main
git push origin dev
#+end_src

**Why this avoids conflicts with =main=**

Conflicts happen when *two histories edit the same lines*. If everyone (or every unfinished idea) commits straight to =main=, you fight those conflicts on the branch that is supposed to stay clean. With =dev=:

1. Daily messy work stays on =dev=
2. =main= only receives finished merges
3. If =dev= and =main= diverge, you resolve conflicts while merging =dev= → =main= (or while updating =dev= from =main=), not while scrambling on production

**If a merge conflict appears**

Git will stop and mark conflicted files. Open them, look for =<<<<<<<= / ======== / =>>>>>>>=, pick the right code, then:

#+begin_src sh
git add .
git commit   # finishes the merge commit if Git asks for one
git push
#+end_src

**Simple rule of thumb for a solo or small project**

1. Start from =main=
2. Create =dev=
3. Build features on =dev= (or on =feature/...= that merges into =dev=)
4. When ready, merge =dev= → =main=
5. Never force unfinished experiments onto =main=

That is the pattern teams mean when they say “don’t develop on main — develop on =dev=, then merge.”

* Everyday workflow after the first push
Once the repo exists, prefer working on =dev= (or a feature branch) instead of committing everything straight to =main=. A typical day:

#+begin_src sh
cd ~/Developer/notes-cli
git checkout dev
git pull origin dev
# edit files...
git status
git add .
git commit -m "Clear message about why you changed things"
git push origin dev
#+end_src

When a batch is ready and tested, merge =dev= into =main= (see the section above). Only use this shorter loop on =main= for tiny, safe fixes if you truly have no =dev= branch yet:

#+begin_src sh
git checkout main
git pull
# small fix...
git add .
git commit -m "Clear message about why you changed things"
git push
#+end_src

Write commit messages for *why*, not only *what*:

- Good: =Fix note.sh crash when notes.txt is missing=
- Weak: =Update files=

If you cloned someone else’s project instead of creating your own:

#+begin_src sh
git clone https://github.com/SOMEUSER/SOME-REPO.git
cd SOME-REPO
#+end_src

* Useful extras
** See what a remote is
#+begin_src sh
git remote -v
#+end_src

** Undo unstaged edits to one file
#+begin_src sh
git restore note.sh
#+end_src

** Unstage a file but keep the edits
#+begin_src sh
git restore --staged note.sh
#+end_src

** Stash work in progress
#+begin_src sh
git stash
git pull
git stash pop
#+end_src

** Mac vs Windows path reminder
| Task | macOS / Git Bash | Windows PowerShell |
|------+------------------+--------------------|
| Home folder | =cd ~= | =cd $HOME= |
| List files | =ls= | =ls= or =dir= |
| Make file executable | =chmod +x note.sh= | often not needed for =.bat=; for bash scripts use Git Bash |
| Copy SSH public key | =pbcopy < ~/.ssh/id_ed25519.pub= | =clip < ~/.ssh/id_ed25519.pub= (Git Bash) |

** Common errors
- *=Permission denied (publickey)=* — SSH key not added to the agent or to GitHub
- *=Authentication failed=* on HTTPS — use a PAT or =gh auth login=, not your GitHub password
- *=rejected (non-fast-forward)=* on push — run =git pull= first, resolve conflicts, then push
- *=Please tell me who you are=* — set =user.name= and =user.email=

* Wrapping up
You do not need every Git command on day one. You need a reliable loop:

=status → add → commit → push=

and enough comfort with =pull=, branches (=main= / =dev= / features), and remotes to not fear the terminal.

On *macOS* and *Windows* the Git vocabulary is the same. Install Git, configure your identity, authenticate to GitHub, then walk a real folder like =notes-cli= from =git init= to a merged pull request.

If you want a next step after this, learn =git diff=, =git rebase -i= (carefully), and how GitHub Actions runs tests on every push — but only after the basics above feel boring. Boring version control is the goal.
